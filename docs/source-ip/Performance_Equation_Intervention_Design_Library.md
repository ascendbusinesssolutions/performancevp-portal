# Part 1 — How to Use This Library

## 1.1 What this is

This is the pattern catalogue the analyst opens at **Stage 3 of an Intervention Design engagement** (Intervention Design Handbook Part 6.2). For each Performance Equation sub-dimension, plus the DLP and the trip-wires, it gives one or more proven intervention design patterns. Each pattern is a **starting structure** the analyst adapts to the validated root cause and the unit's specifics — never a template to apply unmodified.

It is a working document, not a textbook. Use it to find the right pattern fast, confirm it matches your root cause, and design from it.

## 1.2 The design moment this supports

The Library supports **design only**. PerformanceVP designs the intervention and its implementation plan, and states the success criteria for each; the client implements; post-intervention measurement is a separate engagement (a re-run Diagnostic or the Tracking Subscription). So the Library deliberately does **not** carry implementation timelines or measurement detail — those belong to the Intervention Design Handbook (success criteria, Stage 4) and the client's implementation plan. The Library carries only what you need to *design*: the root-cause match, the design shape, the evidence behind it, the plausible effect, the failure modes, and the cross-cutting risks.

## 1.3 How to read a pattern

Every pattern uses the same eight fields, in the same order:

| Field | What it gives you |
|---|---|
| **When to use this pattern** | The validated root causes this pattern fits. Match your Stage 2 output here. |
| **Evidence base** | The research grounding, in one line, with an A/B/C rating. Use it to justify "grounded in established research" in the brief. |
| **Design shape** | The numbered steps of the intervention. The core of the pattern. |
| **Variants** | A pick-by-root-cause table. Choose the variant that matches. |
| **Indicative effect** | A plausible sub-dimension movement range, for competent implementation. Feeds the P-Impact Framework (Handbook Part 6.5). |
| **Pace of change** | How quickly effect typically becomes visible — for managing client expectations, not for implementation planning. |
| **Failure modes** | What to design against. |
| **Watch for** | Trip-wire risks and tight pattern combinations. |
| *Case sketch* | A short illustrative composite showing the pattern in action. |

**Evidence ratings:** **A** — large meta-analytic evidence directly supports this intervention. **B** — strong theory plus supportive studies, but no large meta-analysis on this exact intervention. **C** — strong theoretical case, limited direct empirical testing.

**Case sketches** are illustrative composites, not real client cases. They exist to make the pattern concrete. They will be replaced with (or supplemented by) real anonymised engagement cases as PerformanceVP accumulates them.

## 1.4 Three things every pattern assumes (so they aren't repeated in each)

1. **Competent implementation.** Every indicative effect assumes the intervention is implemented well. Half-hearted structural change or unreinforced behavioural change produces little. The Handbook's effect-estimation (Part 6.4–6.6) adjusts for local implementation readiness.
2. **Source-confidence ceiling.** An expected effect can't be claimed at higher confidence than the Diagnostic's measurement of the target sub-dimension. High-confidence source = full indicative range; Medium/Low widens it.
3. **Binding-constraint multiplier.** The same sub-dimension movement produces different P movement depending on whether the target sits in the binding-constraint component or an already-strong one. The Intervention Design Workbook computes this; the Library's ranges are at sub-dimension level.

## 1.5 Picking a pattern — four quick screens

Before reaching for a pattern, run these:

1. **Structural or behavioural root cause?** Structural causes (a process, policy, threshold, tool, role boundary) take structural designs — faster, more measurable, more durable, and preferred where available. Behavioural causes take behavioural/hybrid designs. Many "culture" problems have structural causes that Stage 2 reveals; the variant tables expose this.
2. **Fast or slow sub-dimension?** The Cadence Master tells you how fast each construct moves. Don't promise the client a faster read than the construct supports — the *Pace of change* line on each pattern reflects this.
3. **Binding constraint?** An intervention on the binding constraint is the highest-priority move and the one expected to produce the largest realistic P gain; one on a non-binding sub-dimension moves P modestly. Be honest in the brief about which case applies.
4. **Trip-wire adjacency?** Some patterns can fire (or extinguish) a trip-wire incidentally. The *Watch for* line flags this.

## 1.6 When no pattern fits

Three valid responses: **adapt** the closest pattern (document the adaptation); **combine** patterns where the root cause has multiple addressable layers; or **design from first principles** using the sub-dimension's theory (Measurement Reference + Strategy Part 1.7), documenting the new pattern for the next refresh. The Library is the floor below which design quality shouldn't fall — not a ceiling on judgement.

## 1.7 A note on the effect ranges

Every indicative effect range is an **evidence-informed estimate**, not a calibrated output — the same honesty discipline as the Strategy's component weights. As PerformanceVP's tracking data accumulates, Pass 3 will tighten these ranges against real expected-vs-actual movement. Never imply more precision than the evidence supports.

## 2.3 Cross-cutting reference (covered once, here)

| Combination | Why they go together |
|---|---|
| M2-P1 + C5-P1 | Low safety caps learning; fix both for compounding effect |
| O1-P1 + DLP-P1 | One decision-rights change often serves both |

| M1-P1 + O4-P1 | A sub-population deep-dive often surfaces capacity stress as the cause |
| M2-P2 + O5-P1 | The same leader coaching often serves safety and enablement |
| O2-P2 + DLP-P3 | Slow information often slows both work and decisions — same fix |
| C2-P2 + C2-P1 | Tacit transfer surfaces some knowledge that turns out documentable |
| C3-P2 + O1/O2/O5 | Injected talent fails if the O-side environment isn't ready for them |

**Sequencing across 2–3 interventions:** binding constraint usually first (highest priority, largest realistic P gain); but lead with a fast win (e.g. S2-P1) if the binding-constraint fix is slow (e.g. C1-P1 build); sequence dependencies (M2 before C5); don't run two interventions in parallel through one overloaded implementer. Operational detail in Handbook Part 8.4.

**Enterprise patterns (cross-unit):** where a portfolio Diagnostic shows the same binding constraint across many units, check whether it's the same root cause or similar symptoms from different causes. Where the cause is genuinely enterprise (e.g. a corporate decision-rights framework), design the structural change once at enterprise level with unit-specific implementation variants. Handbook Part 2.4 covers the engagement architecture.

**Industry context:** the patterns are industry-neutral by default. Where industry materially shifts a pattern, the pattern's *Watch for* line notes it. Deeper industry-archetype variants are a Pass 3 item, pending PerformanceVP's industry-spread engagement experience.

# Part 3 — Capability (C) Patterns

C = 0.35(C1) + 0.15(C2) + 0.20(C3) + 0.20(C4) + 0.10(C5). Component weight α = 0.35 within P.

## 3.1 C1 — Skill

### Pattern C1-P1 — Coverage gap in a role family (buy / build / borrow)

**When to use this pattern.** The unit lacks people with a required skill at sufficient depth. Common validated root causes:
- Role demand has outgrown the hiring/development pipeline.
- A new (often technology-driven) skill has become critical and wasn't invested in.
- Turnover has hollowed out a role family without backfill.
- No capability framework was ever built for the role family, so the gap is structural.

**Evidence base.** Resource-Based View (Barney 1991); strategic HRM / HPWS (Appelbaum et al. 2000; Jiang et al. 2012); training-effectiveness meta-analysis (Arthur et al. 2003, mean d ≈ 0.6–0.7); talent-on-demand framing (Cappelli 2008). **Rating: A.**

**Design shape.**
1. Quantify the gap precisely against the role-required skill framework. Separate urgent gaps (immediate operational impact) from medium-term gaps.
2. Apply buy / build / borrow per gap-driving skill: **buy** (recruit) where acute and scarce internally; **build** (develop) where medium-term and adjacent capability exists; **borrow** (contractor/secondment/partner) where project-bounded or bridging.
3. Sequence by urgency — buy where urgent, build in parallel, borrow to bridge.
4. Design manager reinforcement: new skill isn't applied unless the manager creates space and incentive for it. Set application targets and reinforcement milestones.
5. Build or refresh the capability framework where its absence is part of the cause.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Immediate operational impact | Urgent buy-led | Recruitment; build runs parallel |
| Developable from existing staff; high retention risk on hires | Build-led | Development programme; borrow bridges |
| Framework absent or stale | Framework-rebuild | Build framework first, then act |

**Indicative effect.** +5 to +12 on C1 (buy-led); +4 to +10 (build-led); +6 to +14 where framework-rebuild is included (rebuild improves measurement before real capability moves).

**Pace of change.** Slow. C1 is annual cadence — expect a full cycle before the score moves. Buy-led shows fastest; build-led and framework-rebuild are slower. Manage client expectations toward a 12-month-plus horizon for score movement, with hiring/enrolment milestones as the visible near-term progress.

**Failure modes.**
- Building when the gap is urgent enough to require buying.
- Buying without a retention strategy — talent leaves within 18 months.
- Training without manager reinforcement — skill acquired but not applied.
- Treating the framework as the intervention rather than the precursor to action.

**Watch for.** Pay-equity trip-wire if hires arrive at materially higher pay than incumbents — design the equity story alongside recruitment. Strong C1 movement raises pressure on O1 and O2 (capable people demand the systems to apply their capability).

*Case sketch (illustrative).* A claims unit's C1 sat at 48, binding the whole Capability component. Stage 2 found the gap was concentrated: zero senior claims assessors after two retirements, with junior staff escalating routine claims they should have cleared. Buy-led variant: two senior assessors recruited; a structured "shadow then clear" reinforcement plan so juniors learned the judgement on the job. Framework refreshed to define the assessor skill ladder. C1 designed to move ~+8 over the annual cycle, with escalation-rate drop as the near-term lead signal.

### Pattern C1-P2 — Leadership behavioural capability

**When to use this pattern.** The unit's leaders lack the behavioural competencies for their level, and it acts through their effect on the broader unit. Common validated root causes:
- Promotion-from-within on technical excellence without behavioural development.
- Behavioural expectations uncodified, so leaders can't calibrate.
- Specific behavioural patterns (avoidance of hard conversations, micromanagement, conflict aversion) dragging team outcomes.

**Evidence base.** Leader-development review (Day et al. 2014); 360-feedback meta-analysis (Smither et al. 2005); executive-coaching meta-analysis (Theeboom et al. 2014, g ≈ 0.4–0.6); leader-behaviour/team-outcome meta-analysis (DeRue et al. 2011). **Rating: A** for behaviour-change evidence; effect on downstream team outcomes is reliable but smaller.

**Design shape.**
1. Behavioural diagnostic: 360 against a defined behavioural framework; individual reports plus a cohort-pattern report.
2. Cohort programme on the cohort's common weaknesses, paired with individual coaching (typically 6–10 sessions over 6–9 months) on personal priorities.
3. Engage the cohort's own managers to reinforce and observe — without this layer, change isn't noticed or rewarded and reverts.
4. Re-measure behaviour (360 refresh at 9–12 months); triangulate with direct-report engagement, turnover, and the unit's M2/O5.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Consistent gap across 5+ leaders | Cohort programme | Cohort-level development |
| Gap concentrated in 1–3 leaders | Targeted individual | Individual coaching |
| No behavioural framework exists | Behavioural-framework | Build framework first |

**Indicative effect.** +4 to +8 on the behavioural component of C1 for the cohort; +5 to +10 on O5 for affected teams (O5 moves faster — direct-report perception responds quickly).

**Pace of change.** Mixed. O5 perception (quarterly cadence) can move within a quarter or two. The behavioural C1 component re-reads on the annual cycle. Tell clients: leader behaviour can shift in months, but the capability score confirms it annually.

**Failure modes.**
- Coaching without manager-of-managers engagement — change doesn't survive the boss rewarding old behaviour.
- Generic leadership training instead of targeted behaviour change.
- Avoiding the role-change decision when development clearly fails (make the 12-month decision point explicit).
- Treating 360 as the intervention — it's diagnosis; development is the lever.

**Watch for.** Beneficial cross-effects on M2, O5, M1 in affected teams. Fairness trip-wire risk if development is uneven across the leader cohort.

*Case sketch (illustrative).* A professional-services unit had strong technical leaders but O5 at 51 and rising turnover under two specific partners. Stage 2 confirmed micromanagement and avoidance of development conversations — not a structural issue, a behavioural one. Targeted-individual variant: 360s, eight coaching sessions each, the practice managers briefed to reinforce. O5 designed to move ~+7 across two quarters; behavioural C1 component confirmed at annual refresh.

## 3.2 C2 — Knowledge depth and breadth

### Pattern C2-P1 — Knowledge structure and accessibility

**When to use this pattern.** Knowledge is uneven, undocumented, locked in individuals, or unfindable. Common validated root causes:
- Knowledge concentrated in long-tenured people; departures create cliffs.
- Documentation sparse, stale or unfindable; people work around it by asking.
- Onboarding doesn't set a knowledge baseline; new hires take 9–18 months to competence.
- Regulatory/product knowledge delivered as events without retention reinforcement.

**Evidence base.** Knowledge management theory (Nonaka & Takeuchi 1995; Davenport & Prusak 1998); retention/spacing research (Ebbinghaus; Rohrer & Pashler 2010); transactive memory (Ren & Argote 2011). **Rating: B** — strong theory; implementation quality is the largest moderator.

**Design shape.**
1. Map what knowledge the unit holds and needs — by role family, process, regulatory domain — and who holds it.
2. Triage risk: single-point-of-failure concentrations; stale/contradictory/missing documentation.
3. Apply the structural fix per risk: cross-training and documented handover for single-point-of-failure; assigned curation ownership and refresh cycle for stale docs; a knowledge baseline for new hires (target competence at 90 days, not 9 months).
4. Build reinforcement architecture: spaced micro-assessments for regulatory/product knowledge, not annual events.
5. Align incentives: knowledge contribution recognised; documentation time protected.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Knowledge in 1–3 key individuals | Single-point-of-failure | Documentation + cross-training |
| Slow new-hire ramp | Onboarding-accelerator | Knowledge-baseline build |
| Compliance-knowledge decay | Regulatory-currency | Spaced reinforcement + micro-assessment |

**Indicative effect.** +4 to +9 on C2 generally; +6 to +12 for the onboarding-accelerator variant (it captures every new joiner immediately).

**Pace of change.** Slow. C2 is annual cadence. The onboarding variant shows the fastest practical benefit (each new hire ramps faster) but the score confirms annually. Set client expectation at the annual horizon.

**Failure modes.**
- Platform-first design — buy the tool, assume people populate it.
- Documentation without findability.
- One-off training events without spaced reinforcement.
- Ignoring the knowledge-holder's incentive — experts asked to document without time or recognition stall the work.

**Watch for.** Beneficial cross-effect on C4 (expertise mapping overlaps) and C5 (faster learning). Conditions trip-wire interaction where knowledge gaps create compliance exposure.

*Case sketch (illustrative).* An engineering team's C2 was 55 with a single-point-of-failure: one engineer held all the legacy-system knowledge and was nearing retirement. Single-point-of-failure variant: a documentation project with protected time and recognition, paired with structured cross-training of two successors. C2 designed to move ~+7 by the annual refresh, with documentation-coverage and successor-confidence as near-term signals.

### Pattern C2-P2 — Structured knowledge transfer (mentoring and pairing)

**When to use this pattern.** The knowledge that needs to move is *tacit* — judgement, know-how, contextual understanding that can't be documented into usefulness — and the lever is person-to-person transfer, not documentation or reinforcement. Distinct from C2-P1 (which structures and makes explicit knowledge accessible); here the knowledge resists documentation and only transfers through structured human contact. Common validated root causes:
- Critical know-how is tacit (expert judgement, pattern recognition, relationship knowledge) and lives in a few experienced people.
- A retirement or departure threatens to take tacit knowledge that was never transferable by documentation.
- New or junior staff need the contextual judgement that only comes from working alongside experience.
- Documentation exists but the *application* judgement — when and how to use it — is what's missing.

**Evidence base.** Tacit knowledge theory (Polanyi 1966; Nonaka & Takeuchi 1995); mentoring meta-analysis (Eby, Allen, Evans, Ng & DuBois 2008, *Journal of Vocational Behavior*); cognitive apprenticeship (Collins, Brown & Newman 1989); knowledge-transfer research (Argote & Ingram 2000). **Rating: B** (mentoring effects are meta-analytically supported; tacit-transfer intervention specifics are more practitioner-led).

**Design shape.**
1. Identify the tacit knowledge at risk or in deficit — the judgement and know-how that documentation can't capture, and who holds it.
2. Pair holders with recipients in a structured transfer relationship — not ad hoc mentoring, but defined pairing with transfer goals, protected time, and progression milestones.
3. Use cognitive-apprenticeship structure: the expert models the judgement aloud (thinking visibly), the recipient practises with feedback, support fades as competence builds.
4. Protect the expert's time for transfer and recognise it — without protection, transfer is crowded out by the expert's own delivery load.
5. Capture what *can* be made explicit as a by-product (combine with C2-P1) — the transfer surfaces some knowledge that turns out to be documentable.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Imminent departure of a knowledge holder | Succession-transfer | Intensive paired transfer with deadline |
| Junior staff need contextual judgement | Cognitive-apprenticeship | Modelling + faded support |
| Documentation exists, application judgement missing | Applied-mentoring | Pairing on real work using the docs |

**Indicative effect.** +4 to +9 on C2.

**Pace of change.** Slow. C2 is annual cadence; tacit transfer takes months of structured contact and confirms on the annual cycle. Successor-confidence and the recipient's independent-work milestones are the near-term signals.

**Failure modes.**
- Ad hoc mentoring with no structure, goals or protected time — it doesn't happen.
- Expert time not protected — transfer crowded out by the expert's delivery load.
- Trying to document what is genuinely tacit instead of transferring it person-to-person.
- No faded-support plan — the recipient stays dependent rather than becoming independent.

**Watch for.** Strong overlap with C2-P1 (the explicit-capture by-product) and C4 (transfer builds shared expertise). Beneficial cross-effect on C5 (the recipient learns faster). Low trip-wire risk.

*Case sketch (illustrative).* A claims unit's C2 was 52, with all the complex-case judgement held by two assessors near retirement — knowledge that prior documentation attempts had failed to capture because it was judgement, not procedure. Succession-transfer variant: two structured pairing relationships with protected time, the senior assessors modelling their reasoning aloud on live complex cases while successors practised with feedback and a faded-support timeline. C2 designed to move ~+7 by the annual refresh, successor independent-decision rate as the near-term signal.

## 3.3 C3 — Talent density

### Pattern C3-P1 — Performance management rigour reset

**When to use this pattern.** Ratings are uncalibrated and inflated, so real talent density is unknown and weak performers are carried. Often shows as a 70%+ "exceeding/exceptional" distribution. Common validated root causes:
- Each manager applies a personal standard; no cross-manager calibration.
- Rating-band anchoring statements vague or absent.
- Manager incentives reward kind ratings (fewer hard conversations).
- The PM system rewards process compliance over rating honesty.

**Evidence base.** Performance management literature (Aguinis 2019; Pulakos & O'Leary 2011); rater-error research (Murphy & Cleveland 1995); practitioner talent-review work (McKinsey; Korn Ferry). PerformanceVP's own TDC workshop protocol is grounded here. **Rating: B** — calibration's effect on rating defensibility is well-documented; its effect on actual density depends on the post-calibration action.

**Design shape.**
1. Diagnose the rating problem: pull the distribution; compare to a defensible one (top band ≤25%, bottom ≥5%, archetype-adjusted); find consistently-inflating managers.
2. Build/refresh anchoring statements per band per role family — specific, behavioural, observable.
3. Run cross-manager calibration at the rating cycle (TDC workshop protocol in the Tier 3 Module Library).
4. Target action on the genuinely-low band once revealed — PIPs where development is viable, managed exits where not. Without this step, calibration produces a more honest map but doesn't move density.
5. Develop the inflating managers on rigour and difficult conversations — the lasting structural change.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Distribution unknown/contested | Diagnostic-only | TDC workshop (action becomes separate engagement) |
| Full reset wanted | Full-cycle | Diagnose + calibrate + act + develop managers |
| Rating system itself broken | System-redesign | Redesign scales, process, manager incentives |

**Indicative effect.** First effect is *measurement clarity* — the score often drops to a more honest level before improving. Real movement +4 to +10 on C3.

**Pace of change.** Slow. C3 is annual cadence and density genuinely takes 12–24 months to move (replacement hiring, development). The TDC workshop gives an *immediate* honest baseline, which is itself valuable to surface early — but real improvement is a multi-cycle story. Be explicit with clients that the first honest read may look *worse* before it gets better.

**Failure modes.**
- Treating calibration as the intervention — it's the diagnosis that enables it.
- Managers reverting to inflation next cycle without sustained discipline.
- Brutal calibration without psychological safety — erodes M2 and engagement.
- Replacing without addressing managers' inability to develop their teams.

**Watch for.** Fairness trip-wire risk if calibration is seen as arbitrary or biased. Pay-equity interaction where replacement hires command higher market rates.

*Case sketch (illustrative).* A sales unit reported C3 at 78, contradicted by mediocre results and high carry of underperformers. Stage 2 found 82% of staff rated "exceeding" with no calibration. Full-cycle variant: anchoring statements rebuilt, cross-manager calibration run (true distribution emerged at a C3 nearer 58), PIPs initiated for the genuine low band, managers coached on rigour. C3 designed to move from the *corrected* baseline ~+8 over 18 months — with the honest correction surfaced to the sponsor up front.

### Pattern C3-P2 — Selective talent injection

**When to use this pattern.** Talent density is genuinely low (not just mismeasured) and the gap is best closed by *adding* high-calibre people, not by recalibrating ratings or developing the existing population. Distinct from C3-P1 (which corrects measurement and acts on the low band); here the measurement is sound and the unit simply lacks enough high performers, often in pivotal roles. Common validated root causes:
- The unit has too few people operating at the standard the work requires, confirmed by sound calibration.
- A small number of pivotal roles disproportionately drive unit performance and aren't filled at the right level.
- Recent growth diluted density faster than internal development could replace it.
- The unit has lost several high performers and needs to rebuild the top of the distribution.

**Evidence base.** Talent-density and "topgrading" practitioner research (Smart 2005); the star-performer and pivotal-role literature (Aguinis & O'Boyle 2014, *Personnel Psychology* on the heavy-tailed distribution of performance; Boudreau & Ramstad 2007 on pivotal roles). **Rating: B.**

**Design shape.**
1. Confirm density is genuinely low, not inflated-then-corrected — this pattern assumes sound C3 measurement (if ratings are inflated, run C3-P1 first).
2. Identify the pivotal roles — the small set where a high performer disproportionately moves unit output.
3. Design the injection: targeted senior/specialist hiring into pivotal roles; selective internal promotion of genuine high performers; strategic redeployment of strong people from elsewhere.
4. Pair with retention of the existing high performers — injecting talent while losing current strength is a net wash.
5. Manage integration — high-calibre injections fail if the receiving environment (O-side: tools, decision rights, leadership) frustrates them; check the O-side is ready.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Pivotal roles under-filled | Pivotal-hire | Targeted senior/specialist recruitment |
| Genuine high performers ready | Selective-promotion | Internal promotion |
| Strong people available elsewhere internally | Redeployment | Strategic internal moves |

**Indicative effect.** +4 to +10 on C3, concentrated where the injection hits pivotal roles.

**Pace of change.** Slow. C3 is annual cadence and senior hiring carries lead time. The effect is real but confirms over the annual cycle; pivotal hires can shift unit output before the score moves.

**Failure modes.**
- Injecting talent into an unready O-side environment — high performers arrive, get frustrated, and leave.
- Adding density while losing it — no retention of existing strength.
- Treating injection as a substitute for C3-P1 where ratings are actually inflated — adding people to a unit that can't see its real distribution.
- Hiring senior people without pivotal-role focus — density rises on paper but unit output doesn't.

**Watch for.** Pay-equity trip-wire risk where senior injections command materially higher pay than incumbents — design the equity story. Fairness interaction where external injection is perceived to block internal progression; pair with selective-promotion where genuine internal candidates exist. Strong dependency on the O-side being ready (combine O1/O2/O5 where needed).

*Case sketch (illustrative).* A product unit's C3 was a soundly-measured 54 after recent rapid growth had diluted a once-strong team. Stage 2 confirmed the measurement and isolated two pivotal lead roles sitting vacant or under-filled. Pivotal-hire variant: targeted recruitment of two senior product leads, paired with retention investment in the three existing strong performers and an O-side check that decision rights would let the new hires operate. C3 designed to move ~+7 over the annual cycle.

## 3.4 C4 — Collective intelligence

### Pattern C4-P1 — Expertise clarity and transactive memory

**When to use this pattern.** Team members don't know who knows what; expertise is siloed, invisible or duplicated. Common validated root causes:
- Team is large, remote or hybrid, with low visibility into each other's expertise.
- Team is new or recently reshaped; transactive memory hasn't formed.
- Specialist knowledge is implicit and only surfaces by accident.
- Rigid cross-team boundaries stop expertise flowing.

**Evidence base.** Transactive memory systems (Wegner 1986; Lewis & Herndon 2011; Ren & Argote 2011); TMS-performance meta-analysis (Peltokorpi & Hood 2019, moderate-to-large effects); expertise recognition (Bunderson 2003); network analysis (Cross & Parker 2004). **Rating: A.**

**Design shape.**
1. Map the team's actual expertise collaboratively — formal qualifications, informal capabilities, project history, domain depth.
2. Build a searchable, current expertise directory (usually in the existing collaboration platform); assign maintenance ownership and a quarterly refresh.
3. Install structured cross-exposure: tech talks, expertise spotlights, paired work across specialisms, rotations where scope allows.
4. Set routing rituals — explicit norms for finding expertise so the directory is the routing tool, not a one-time exercise.
5. Where the unit spans teams, add cross-boundary forums (communities of practice, guilds, cross-team retros).

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Small (<15), stable team | Mapping-only | Mapping + directory maintenance |
| New/merged/remote team, low TMS | Cross-exposure-heavy | Sustained cross-exposure |
| Gap is between teams, not within | Cross-boundary | Communities of practice / guilds |

**Indicative effect.** +5 to +10 on C4, with Expertise Clarity moving first and Expertise Flow lagging.

**Pace of change.** Moderate. C4 is half-yearly cadence (one Expertise Flow item in the quarterly pulse). Clarity can shift within a quarter; Flow takes longer. Set client expectation at the half-yearly read for a real signal.

**Failure modes.**
- A directory nobody maintains — stale within 90 days.
- Mapping without changing routing — documentation that doesn't change behaviour.
- Mandated knowledge-sharing forums — compliance, not transactive memory.
- Treating expertise as static — TMS needs continuous refresh.

**Watch for.** Beneficial cross-effects on C2, C5, and M1 (people feel known for their expertise). No direct trip-wire risk.

*Case sketch (illustrative).* A 40-person product team formed from three merged squads scored C4 at 46 — people solved problems alone that colleagues had already solved. Cross-exposure-heavy variant: collaborative expertise mapping, a maintained directory, fortnightly expertise spotlights, and paired work across the old squad lines. C4 designed to move ~+7 by the half-yearly health check, Clarity leading Flow.

## 3.5 C5 — Learning velocity

### Pattern C5-P1 — Learning system redesign

**When to use this pattern.** The team learns slowly — slow ramp-up, lessons that don't transfer, event-based rather than continuous skill development. Common validated root causes:
- Retrospectives absent, perfunctory, or producing no action.
- Unsystematic onboarding; each joiner reinvents the path.
- Manager focus exclusively on delivery; no protected learning time.
- Failure treated as fault, not data — no safety to learn from mistakes.

**Evidence base.** Learning-organisation theory (Senge 1990; Edmondson 1999 team learning); deliberate practice (Ericsson et al. 1993); learning-from-failure (Edmondson 2011; Cannon & Edmondson 2005); software-delivery evidence (Forsgren et al. 2018, *Accelerate*). **Rating: B.**

**Design shape.**
1. Diagnose the learning bottleneck — onboarding, post-incident, or skill transfer.
2. Install structured retrospectives at a cadence matching work cycle; lessons tracked to action with named owners.
3. Systematise onboarding: documented 30/60/90-day expectations; buddy/mentor; skill-milestone ramp rather than tenure assumptions.
4. Build deliberate-practice loops on the 2–3 most critical skills (peer review, coaching, simulation).
5. Protect learning time (typically 10–20%), defended by the manager against delivery pressure.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Has time, lacks the practice | Retrospective-focused | Embed retrospective discipline |
| High churn / recent growth | Onboarding-acceleration | Time-to-competence focus |
| Specific skill weaknesses limiting performance | Deliberate-practice | Feedback loops on those skills |

**Indicative effect.** +5 to +10 on C5.

**Pace of change.** Slow to confirm. C5 is annual cadence (12-month rolling metric), though the underlying data feeds monthly. Practices can be installed in weeks and benefits felt quickly; the score confirms over the annual window. Manage expectations toward "practices change fast, the metric confirms over a year."

**Failure modes.**
- Retrospectives that produce no action — ceremony.
- Learning time that gets eaten by delivery within weeks unless actively protected.
- Treating learning as event-based.
- Low psychological safety degrading retrospectives into blame — address M2 first or in parallel.

**Watch for.** Strong M2 dependency — low M2 caps C5 movement (combine with M2-P1). Beneficial cross-effects on M1 and C4.

*Case sketch (illustrative).* A delivery team's C5 was 49; incidents recurred because lessons evaporated and new joiners took six months to contribute. Retrospective-focused variant: structured sprint retrospectives with tracked actions, plus a documented 30/60/90 onboarding path. C5 designed to move ~+6 over the annual window, with incident-recurrence and time-to-first-contribution as near-term signals.

### Pattern C5-P2 — External capability injection

**When to use this pattern.** The team needs to learn something genuinely new — a method, technology or domain it has no internal seed of — and internal learning-system redesign (C5-P1) can't accelerate what isn't there to begin with. The lever is bringing external capability in to seed and transfer it. Distinct from C5-P1 (which optimises how the team learns from its own experience); here the team can't learn its way to a capability it has never held. Common validated root causes:
- A new technology or method the team has no internal exemplar of.
- A step-change in domain requirements outpacing organic learning.
- Repeated failed attempts to self-teach a capability with no internal anchor.

**Evidence base.** Absorptive-capacity theory (Cohen & Levinthal 1990, *Administrative Science Quarterly*); knowledge-transfer research (Argote & Ingram 2000, *Organizational Behavior and Human Decision Processes*); the deliberate-practice literature (Ericsson et al. 1993) on the role of expert models. **Rating: B.**

**Design shape.**
1. Define precisely the capability the team needs to acquire and confirm there is no internal seed to grow from (if there is, C5-P1 or C1-P1 build-variant is the better lever).
2. Bring in the external capability in a *transfer* configuration, not a delivery one — an expert practitioner, embedded coach, or partner who works alongside the team with explicit transfer obligations, not one who does the work for them.
3. Structure the transfer: paired work, the external expert as a working model, documented practices the team builds as they learn.
4. Set an explicit exit — the external capability withdraws on a planned timeline as internal capability builds, so the team doesn't become dependent.
5. Reinforce with C5-P1 practices so the newly-seeded capability keeps developing after the external input leaves.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| New technology/method, no internal exemplar | Embedded-expert | Expert works alongside with transfer obligation |
| Step-change in domain requirements | Partner-transfer | Partner seeds capability, plans exit |
| Failed self-teaching attempts | Coach-led | Coaching against an expert model |

**Indicative effect.** +5 to +12 on C5 where transfer is genuine and the exit is managed; lower if the external input does the work rather than transferring it.

**Pace of change.** Slow to confirm. C5 is annual cadence; the capability seeds during the engagement but the score confirms over the annual window. The transfer itself typically runs several months.

**Failure modes.**
- External capability that delivers rather than transfers — the team never learns and dependency sets in.
- No managed exit — the "temporary" expert becomes permanent and internal capability never forms.
- Seeding capability without C5-P1 reinforcement — it doesn't keep developing after the expert leaves.
- Bringing in external capability where an internal seed existed — slower and costlier than growing it (C1-P1 build).

**Watch for.** Beneficial cross-effects on C1 (skill) and C4 (new expertise to share). Pay-equity/fairness interaction is low but watch contractor-vs-incumbent pay optics if the external party is visible and well-paid.

*Case sketch (illustrative).* An analytics team's C5 was 47 and it had failed twice to self-teach machine-learning productionisation — there was no internal exemplar to learn from. Embedded-expert variant: an ML engineer embedded for four months in a paired-work transfer configuration with a planned exit, the team documenting practices as they built them, C5-P1 retrospectives reinforcing afterward. C5 designed to move ~+8 over the annual window.

# Part 4 — Motivation (M) Patterns

M = 0.50(M1) + 0.20(M2) + 0.15(M3) + 0.15(M4), with three trip-wires as critical-finding overlays. Component weight β = 0.40 within P (the largest component).

## 4.1 M1 — Engagement and confidence

### Pattern M1-P1 — Sub-population deep-dive and targeted response

**When to use this pattern.** The unit's M1 average looks acceptable but behavioural triangulators (turnover, absence, internal application) tell a worse story — a sub-population is in trouble that the average masks. Common validated root causes:
- A demographic or role-family sub-population is materially less engaged than average.
- One manager's team accounts for most of the drag.
- A recent event hit one subgroup disproportionately.
- Workload or recognition is concentrated on the affected group.

**Evidence base.** Job demands–resources (Demerouti et al. 2001; Bakker & Demerouti 2017); work-engagement meta-analysis (Halbesleben 2010); sub-population variation (Kacmar et al. 2006). **Rating: A.**

**Design shape.**
1. Cut the engagement data by team, demographic, tenure, role family, manager. Find the sub-population driving the drag.
2. Run targeted listening with the affected group (focus groups, manager listening, structured 1:1s) to find the specific demands or missing resources.
3. Apply the targeted response to the specific cause — workload rebalance, manager change/coaching, recognition design, role redesign, retention investigation. Not a generic engagement programme.
4. Monitor the affected group's behavioural triangulators monthly to confirm before the next M1 read.
5. Engage the affected team's manager as implementer (unless the manager *is* the cause — see manager-specific variant).

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Drag in one manager's team | Manager-specific | Manager development (overlaps O5-P1) |
| Workload-driven | Workload | Capacity rebalance (overlaps O4-P1) |
| Recognition-driven | Recognition | Recognition redesign |
| "No future here" | Career-pathing | Career conversations + internal mobility |

**Indicative effect.** +3 to +8 on M1 for the affected sub-population; +2 to +5 on unit-level M1 (depending on the sub-population's size).

**Pace of change.** Fast. M1 is quarterly cadence — the fastest-moving motivation construct. Behavioural triangulators read monthly. A sub-population pulse signal can appear at the next quarter. Good news for managing client expectations: this is one of the quicker wins.

**Failure modes.**
- Acting on the unit average when the issue is concentrated.
- One-off listening with no follow-through — erodes trust further.
- Treating engagement as cause rather than effect — the cause is demands-resources imbalance.
- The implementer-manager being part of the cause (use the manager-specific variant).

**Watch for.** Sub-population analysis sometimes surfaces a trip-wire (fairness, pay equity) — handle per Part 8. Strong cross-effects with O4, O5, and C1 (frustrated capable people).

*Case sketch (illustrative).* A contact-centre unit's M1 sat at a respectable 68, but turnover ran hot. Cut by tenure, the 0–12-month cohort was at 44 and leaving fast. Career-pathing variant: structured early-career conversations, a visible progression path, and a buddy system. The sub-population M1 was designed to move ~+6 within two quarters, with the cohort's turnover as the lead signal.

---

### Pattern M1-P2 — Confidence and efficacy lift

**When to use this pattern.** Engagement is acceptable but shared belief in the team's ability to succeed is low — usually after a visible failure, sustained underperformance, or a run of events that eroded collective confidence. Common validated root causes:
- A recent visible failure shook team belief.
- Goals disconnected from capability/opportunity produced sustained underperformance.
- Leadership communication emphasises threats and shortfalls, not progress.
- No visible recent wins to anchor confidence.

**Evidence base.** Collective efficacy (Bandura 1997; Stajkovic et al. 2009 meta-analysis, r ≈ 0.35); team potency (Guzzo et al. 1993); feedback-intervention meta-analysis (Kluger & DeNisi 1996). **Rating: A.**

**Design shape.**
1. Recalibrate 1–2 key goals to genuine-reach difficulty — high enough to engage effort, attainable with focus.
2. Engineer visible near-term wins; sequence and resource the team to deliver them. The single largest efficacy lever.
3. Surface vicarious efficacy — expose the team to peer teams that overcame similar challenges.
4. Redesign leader communication toward recognising progress and naming capabilities applied, without papering over real problems.
5. Build retrospectives that surface what's working, not only what's failing.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| After a visible failure | Post-failure | Near-term wins + honest accounting |
| Goals beyond capability | Stretched-goals | Goal recalibration |
| Wins exist but aren't reinforced | Communication | Leader communication redesign |

**Indicative effect.** +3 to +7 on M1 (team-confidence component).

**Pace of change.** Fast. Efficacy responds quickly to visible wins — quarterly pulse will pick it up. Among the more responsive interventions.

**Failure modes.**
- Manufactured wins the team sees as cosmetic — lower efficacy, not raise it.
- Communication unsupported by reality — read as gaslighting.
- A burst of wins followed by reversion to the old pattern.
- Ignoring the cause of the original failure — another failure cycle.

**Watch for.** Beneficial cross-effects with O1 (confident teams need clear authority) and C5 (efficacy enables learning risk-taking).

*Case sketch (illustrative).* A product team that had shipped a high-profile failure scored engagement at 64 but team-confidence items far lower. Post-failure variant: an honest retro on the failure, two genuinely winnable next deliverables resourced and sequenced, and a shift in the leader's stand-ups toward naming progress. The confidence component of M1 was designed to move ~+5 within two quarters.

## 4.2 M2 — Psychological safety

### Pattern M2-P1 — Structural psychological safety

**When to use this pattern.** Low M2 is driven by a structural feature, not diffuse culture. Common validated root causes:
- Incident/error reporting handles disclosure with individual accountability before systems analysis.
- Speaking up has been visibly punished recently.
- Performance management treats disclosed errors as ratings-relevant.
- A specific manager's response pattern is shaped by their structural incentives (combine M2-P2 if behaviour dominates).

**Evidence base.** Psychological safety (Edmondson 1999; Edmondson & Lei 2014; Frazier et al. 2017 meta-analysis); Just Culture (Reason 1997; Dekker 2007); high-reliability organisations (Weick & Sutcliffe 2007). **Rating: A.**

**Design shape.**
1. Identify which structural feature is the chilling agent — incident review, speak-up channel, performance management, or a manager's incentive-shaped response.
2. Redesign it. Incident review → Just Culture distinctions (honest error / at-risk / reckless, proportionate response). Speak-up → channel and response-protocol rebuild with visible fair outcomes. PM → separate disclosure data from evaluation.
3. Have the leader visibly demonstrate the new approach in the first few cases — without this, the change reads as cosmetic.
4. Communicate the approach, rationale and expectations. Repeated, not once.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Punitive incident review | Just Culture | Incident-review redesign |
| Distrusted speak-up channel | Speak-up redesign | Channel + protocol rebuild |
| PM penalises disclosure | PM separation | Decouple disclosure from rating |
| Manager incentive-driven behaviour | Combine with M2-P2 | Coaching + incentive change |

**Indicative effect.** +5 to +10 on M2. Among the more responsive interventions — the structural change is immediately visible.

**Pace of change.** Fast. M2 is quarterly cadence and structural safety changes are visible quickly. But confirm at the half-yearly read — an early pulse rise can be announcement-effect halo, not durable change.

**Failure modes.**
- Process change written but the first few cases handled the old way.
- Redesigning around a problem manager without addressing the manager.
- Declaring success at the first pulse.
- Treating rising disclosure rates as failure — they usually signal success.

**Watch for.** Frequent beneficial cross-effects on C5, S3, M1. Fairness trip-wire risk if Just Culture produces visibly different responses across cases that look similar from outside.

*Case sketch (illustrative).* A hospital operations unit scored M2 at 42; Stage 2 found a blame-first incident-review process. Just Culture variant: incident review redesigned around the honest-error/at-risk/reckless distinction, the unit director personally modelling it on the first three incidents, and clear communication of the change. M2 designed to move ~+8, confirmed at the half-yearly; disclosure rates expected to rise (a good sign) before settling.

---

### Pattern M2-P2 — Leader-behaviour psychological safety

**When to use this pattern.** Low M2 is driven by a leader's behaviour, not a structural cause. Common validated root causes:
- The leader's response to bad news is sharp, dismissive or escalatory.
- The leader visibly punishes dissent.
- The leader never models vulnerability (never admits error or uncertainty).
- The leader's stress response under pressure is unsafe.

**Evidence base.** Leader behaviour and safety (Edmondson 2003; Nembhard & Edmondson 2006); coaching meta-analysis (Theeboom et al. 2014); transformational leadership meta-analysis (Judge & Piccolo 2004). **Rating: A** for the mechanism; **B** for development effectiveness at this specific outcome.

**Design shape.**
1. Targeted 360 on safety-supporting behaviours (response to disclosure, disagreement, error), direct-report-rich.
2. Individual coaching (6–10 sessions over 6–9 months) with specific behavioural goals from the 360.
3. Add a real-time feedback mechanism — a trusted peer or coach observing team interactions — so self-perception doesn't drift from team perception.
4. Engage the leader's own manager to reinforce; without it, the stress response reverts under pressure.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Safe generally, unsafe under pressure | High-stakes-only | Stress-response focus |
| Habitual, not stress-bound | Pattern-wide | Broader behavioural change |
| Role genuinely too demanding | Combine with role redesign | Coaching + role boundary work |

**Indicative effect.** +4 to +8 on M2 in the affected team. Highly dependent on leader receptivity — low receptivity should surface in Stage 2 and may point to role change, not development.

**Pace of change.** Moderate. M2 quarterly pulse gives a first read at three months; direct-report behavioural pulse can run faster (60 days). Manage expectations: behaviour can shift within a quarter, durability confirms over two.

**Failure modes.**
- Coaching a leader whose incentives reward the unsafe behaviour.
- Coaching without manager-of-manager engagement.
- Avoiding the role-change decision when development has demonstrably failed (no 360 movement at 6 months).
- Declaring success at the announcement — intent isn't change.

**Watch for.** Where the leader's behaviour drove fairness perceptions, the fairness trip-wire may move with the intervention. Strong cross-effects on M1 and O5.

*Case sketch (illustrative).* A finance team's M2 was 47, isolated to one manager whose stress response was to publicly criticise. High-stakes-only variant: a focused 360, coaching targeting the pressure response, and the manager's director briefed to reinforce calm under deadline. M2 in the team designed to move ~+6 across two quarters.

## 4.3 M3 — Autonomous motivation

### Pattern M3-P1 — Autonomy-supportive job and management redesign

**When to use this pattern.** Work is experienced as externally controlled, producing compliance-grade effort rather than initiative. Common validated root causes:
- Roles over-specified at task level; the *how* is dictated.
- Managers manage outputs by directing inputs (micromanagement).
- PM is heavily process-compliance-oriented.
- Recognition rewards conformity, not initiative.

**Evidence base.** Self-Determination Theory (Deci & Ryan 1985, 2017; Cerasoli et al. 2014 and Van den Broeck et al. 2016 meta-analyses); job design (Hackman & Oldham 1976; Parker 2014); autonomy-support management (Gagné & Deci 2005; Slemp et al. 2018 meta-analysis). **Rating: A.**

**Design shape.**
1. Audit role design for task-level over-specification; separate necessary specification (compliance, safety, integration) from unnecessary (preferences dressed as requirements).
2. Lift outcome clarity — people given clear outcomes and method-freedom show higher autonomous motivation than the reverse.
3. Develop managers on autonomy-supportive practices: ask before telling; give rationale for constraints; offer choice within constraints; solicit input on the *how*.
4. Redesign recognition to reward improvement and initiative, not only conformity.
5. Make genuine constraints explicit and minimal, with their rationale — autonomy is experienced within constraints, not in their absence.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Task-level over-specification in role design | Job-redesign | Role architecture redesign |
| Manager behaviour despite OK role design | Manager-practice | Manager development |
| Recognition system rewards the wrong thing | Recognition-redesign | Recognition system change |

**Indicative effect.** +4 to +9 on M3.

**Pace of change.** Slow. M3 is annual cadence — closer to disposition than mood, so meaningful movement takes a year or more. Manager-behaviour pulses read faster. Be clear with clients this is a slower lever than M1.

**Failure modes.**
- Autonomy in name only — telling people they have autonomy while directing the *how*.
- Autonomy without competence — pair with C1/C5 where competence is the gap.
- Manager training without role-design change where the role is genuinely over-specified.
- Recognition system left rewarding conformity, contradicting the manager signal.

**Watch for.** Beneficial cross-effects on M1, M4 and C5. Fairness trip-wire risk where autonomy is granted unevenly without clear rationale.

*Case sketch (illustrative).* A back-office processing team scored M3 at 50 — high compliance, no initiative. Stage 2 found roles scripted to the keystroke and managers checking everything. Manager-practice variant (with light job-redesign): managers coached to set outcomes and trust the path, scripts loosened to the genuinely-necessary controls. M3 designed to move ~+6 over the annual cycle, with manager-behaviour pulse as the near-term signal.

## 4.4 M4 — Purpose alignment

### Pattern M4-P1 — Purpose translation and personal connection

**When to use this pattern.** Corporate purpose doesn't translate to the unit's work; people can't connect day-to-day work to a meaningful outcome. Common validated root causes:
- Corporate purpose statements are abstract and never translated to the unit.
- Leaders rarely articulate the work-outcome connection.
- Recognition celebrates delivery, not the outcome it served.
- Recent changes disconnected current work from the original narrative.

**Evidence base.** Meaningful-work review (Rosso et al. 2010; Bailey et al. 2019); job crafting (Wrzesniewski & Dutton 2001; Tims et al. 2013); leader meaning-making (Carton et al. 2014); CSR-engagement (Glavas 2016). **Rating: B.**

**Design shape.**
1. Translate purpose to the unit's work — a unit-specific "why our work matters" statement, derived collaboratively (not a values statement).
2. Build leader meaning-making practice — articulate the purpose-work connection in regular communication. The change is repeated articulation, not a one-off rollout.
3. Redesign recognition to surface outcomes, not just outputs ("we shipped X and Y customers can now Z").
4. Create customer/outcome exposure — customer stories, downstream feedback, impact data. Visible outcome data is a large lever on meaning.
5. Give job-crafting permission where roles allow.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Corporate purpose exists, not translated | Translation | Translation + ongoing articulation |
| Recent change disconnected the narrative | Reconnection | Reconnect the narrative |
| Unit operationally distant from outcomes | Outcome-exposure | Structured outcome exposure |

**Indicative effect.** +3 to +7 on M4.

**Pace of change.** Slow. M4 is annual cadence and the slowest-moving M sub-dimension — it requires sustained leader practice. The slowest of the motivation levers; set expectations accordingly.

**Failure modes.**
- A purpose-statement project nobody refers to.
- Leader articulation that isn't believed — reduces M4.
- Cherry-picked, manufactured outcome exposure.
- Trying to manufacture meaning where the work genuinely doesn't connect — be honest about the lever's limits.

**Watch for.** Beneficial cross-effects on M1, M3, and retention. Fairness trip-wire risk where purpose communication implies all work is meaningful when some genuinely isn't.

*Case sketch (illustrative).* A compliance team scored M4 at 53 — they saw their work as box-ticking. Outcome-exposure variant: structured exposure to the customer-harm cases their work prevented, plus recognition reframed around protection outcomes. M4 designed to move ~+5 over the annual cycle.

# Part 5 — Opportunity (O) Patterns

O = 0.30(O1) + 0.25(O2) + 0.20(O3) + 0.10(O4) + 0.15(O5). Component weight γ = 0.25 within P.

## 5.1 O1 — Clarity and decision rights

### Pattern O1-P1 — Decision-rights reset

**When to use this pattern.** Decision rights are unclear or unfit — people don't know who decides, decisions escalate unnecessarily or get re-made. May show in audit and survey, or as an audit-perception gap (documented but not lived). Common validated root causes:
- Decision rights undocumented; evolved by habit and personality.
- Documented but never communicated.
- Documented and communicated but a specific manager overrides them.
- Approval thresholds contradict documented delegation.
- Documented for steady state but not for the situations actually faced.

**Evidence base.** Decision-rights / org-design (Brickley, Smith & Zimmerman 2009; Jensen & Meckling 1992); RAPID framework (Rogers & Blenko 2006; Blenko et al. 2010); role-ambiguity meta-analysis (Tubre & Collins 2000). **Rating: B.**

**Design shape.**
1. Sample 15–25 of the unit's actual decisions (use the DLP sample where available) across operational/tactical/strategic.
2. Apply a decision-rights framework (RAPID/RACI/DACI — the discipline matters more than the framework): for each decision, who Recommends / Inputs / Decides / Performs / Owns.
3. Resolve the validated root cause: communication gap → systematic re-communication + leader reinforcement; manager override → confront directly (combine O5-P1/M2-P2); threshold contradiction → raise thresholds to match delegation; documentation gap → document with rights-holders present.
4. Test against the next 5–10 real decisions; adjust where the framework creates friction.
5. Maintain with a quarterly check — without it, the same problems re-emerge.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Documentation correct but unknown | Communication | Sustained re-communication |
| Thresholds undermine delegation | Threshold | Threshold change |
| A manager overrides | Manager-override | Combine with M2-P2 / O5-P1 |
| Undocumented, habit-evolved | Build-from-scratch | Full RAPID/RACI build |

**Indicative effect.** +5 to +12 on O1. Among the more measurable — the structural change is visible and perception responds.

**Pace of change.** Moderate. O1 survey is half-yearly (audit annual); DLP operational quarterly. The decision-latency signal often moves first (decisions stop being relitigated). Set the first real O1 read at the half-yearly.

**Failure modes.**
- Re-communicating when the real cause is structural override.
- Fixing the document rather than the lived experience.
- Over-specifying every decision — produces a thick document and the same vague reality.
- Stopping at the unit boundary when decisions cross into adjacent units.

**Watch for.** Beneficial cross-effects on M3 (autonomy), DLP (operational), O5. Fairness trip-wire risk where new rights concentrate in certain roles.

*Case sketch (illustrative).* An operations unit's O1 was 52 with a 22-point audit-perception gap — rights documented, not lived. Stage 2 found a manager routinely overriding delegated calls. Manager-override variant: the RAPID framework re-affirmed, the override pattern confronted directly via O5-P1 coaching, decisions tested against the next ten real cases. O1 designed to move ~+9 by the half-yearly, gap closing as the lead signal.

---

### Pattern O1-P2 — Cascade alignment

**When to use this pattern.** The unit can't connect its work to enterprise strategy; the strategic-cascade audit shows breaks between enterprise objectives and team outcomes. Common validated root causes:
- Strategy communicated but not cascaded; each layer interprets differently.
- The goal-setting system is treated as compliance, not alignment.
- The cascade produces volume not focus — every team has 8 loosely-connected objectives.
- Strategic priorities change faster than the cascade keeps up.

**Evidence base.** Strategy maps / Balanced Scorecard (Kaplan & Norton 1992, 2001); goal-setting (Locke & Latham 1990; Epton et al. 2017 meta-analysis); strategy-execution (Sull et al. 2015). **Rating: B** (goal-setting itself is A-level; cascade-specific intervention evidence is more practitioner-led).

**Design shape.**
1. Audit the cascade: trace 5–10 team/individual objectives back to enterprise objectives; find the breaks.
2. Rebuild it: each layer translates the layer above into a small number of focused objectives — connection and focus, not coverage.
3. Constrain volume to 3–5 objectives per layer.
4. Make the cascade visible and traceable (platform or document) — visibility is half the lever.
5. Establish a quarterly cascade review to re-align as strategy evolves.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| OKR exists in name only | OKR-implementation | Implementation discipline |
| Too many objectives per team | Strategy-volume | Reduction, not addition |
| Cascade broken at a specific layer | Cascade-rebuild | Rebuild from that layer |

**Indicative effect.** +4 to +10 on O1 (cascade component).

**Pace of change.** Moderate-slow. O1 survey half-yearly; cascade behaviour takes a full strategy cycle to embed. M4 (purpose) benefit reads at annual. Slower than O1-P1.

**Failure modes.**
- OKR as theatre — motions without cascade discipline.
- Cascade rebuild as a one-off — goes stale within two cycles without quarterly maintenance.
- Imposing volume from above — unit discipline can't fix enterprise over-objective-setting.

**Watch for.** Strong beneficial cross-effect on M4 (purpose). M3 cross-effect (autonomy within clarity of what matters).

*Case sketch (illustrative).* A marketing unit's O1 cascade items were low; people couldn't say how their work served the company strategy. Strategy-volume variant: each team's 9 objectives cut to 4, each traceable to an enterprise objective, with a quarterly review installed. O1 cascade component designed to move ~+6 by the half-yearly, M4 benefit confirming at annual.

## 5.2 O2 — Tools and information

### Pattern O2-P1 — Tool rationalisation and integration

**When to use this pattern.** Too many tools, poor integration, or a critical tool missing — cost shows in time lost to tool friction, manual-handoff errors, and frustration. Common validated root causes:
- Tool sprawl: overlapping tools, none done well.
- Integration gaps requiring manual data movement.
- A class of work without the tool it needs.
- Centrally-mandated tools that don't fit the actual work.

**Evidence base.** Sociotechnical systems (Trist 1981; Pasmore et al. 1982); technology acceptance / UTAUT (Venkatesh et al. 2003); delivery-tooling evidence (Forsgren et al. 2018). **Rating: B.**

**Design shape.**
1. Inventory tools — what's used, for what, by whom, what overlaps.
2. Map the actual workflow — where people switch tools or move data by hand.
3. Rationalise — eliminate redundant tools; pick one where two do the same job and migrate.
4. Integrate where the gap is structural; where integration is prohibitive, design the manual workflow to minimise friction.
5. Fill critical gaps with the right tool plus the practices to use it.
6. Provide sustained adoption support — training, champions, manager reinforcement.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Tool sprawl | Rationalisation-led | Consolidation |
| Right tools, disconnected | Integration-led | Integration |
| Critical tool missing | Gap-fill | Tool acquisition + adoption |

**Indicative effect.** +5 to +12 on O2.

**Pace of change.** Moderate. O2 is half-yearly; single-tool gaps can show faster, broad rationalisation slower. Major rollouts can trigger an event-triggered refresh (Cadence Master Part 4.2).

**Failure modes.**
- Tool replacement without process redesign.
- Big-bang adoption without support — productivity dips and reversion is requested.
- Mandated tool that doesn't fit — needs a central conversation, not unit-only design.
- Ignoring shadow IT — if people work around official tools, the inventory is incomplete.

**Watch for.** Beneficial cross-effects on O3, S2, C5 (where new tools include AI). Conditions trip-wire risk where tool gaps create unsafe/non-compliant work.

*Case sketch (illustrative).* A sales operations team scored O2 at 49 across four overlapping CRMs-of-record. Rationalisation-led variant: consolidation to one system, the others retired with migration support and champions. O2 designed to move ~+8 by the half-yearly, ITSM ticket volume as the near-term signal.

### Pattern O2-P2 — Information access redesign

**When to use this pattern.** The *tools* are adequate but people can't get the *information* they need to do their work — data is locked in systems they can't access, scattered across sources they must assemble manually, or available but not in a usable form. Distinct from O2-P1 (which fixes the tools); here the tools are fine and the problem is data access, reporting and information flow. Common validated root causes:
- Data exists but is locked behind access controls, teams or approval gates.
- Information must be assembled manually from multiple systems for routine work.
- Reporting is absent, stale, or doesn't answer the questions the work actually asks.
- People lack a single trusted source and waste time reconciling conflicting data.

**Evidence base.** Information-processing view (Galbraith 1974); data-quality and information-management research; sociotechnical systems (Trist 1981). **Rating: B.**

**Design shape.**
1. Map the information the unit needs for its core work — what data, for which decisions and tasks, currently sourced how.
2. Find the access bottlenecks — locked data, manual assembly, missing or untrusted reporting.
3. Fix access structurally: appropriate data-access provisioning; a single trusted source where conflicting sources exist; self-serve reporting for recurring information needs.
4. Build the reporting/views the work actually needs — designed around the questions the unit asks, not the data that happens to be available.
5. Provide adoption support so the new access and views are used rather than worked around.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Data locked by access controls | Access-provisioning | Provision appropriate access |
| Manual assembly from many sources | Self-serve-reporting | Build the recurring views |
| Conflicting/untrusted sources | Single-source | Establish the trusted source |

**Indicative effect.** +4 to +10 on O2.

**Pace of change.** Moderate. O2 is half-yearly; access-provisioning fixes can show fast, reporting/data-platform work slower. Often overlaps with DLP-P3 where slow information also slows decisions.

**Failure modes.**
- Building reporting around available data rather than the questions the work asks.
- Provisioning access without governance — solving a friction problem by creating a data-risk problem.
- A single-source initiative that doesn't retire the conflicting sources — people keep using the old ones.
- Self-serve views nobody maintains.

**Watch for.** Strong overlap with DLP-P3 (information latency) — often the same design. Conditions/compliance interaction where data access touches sensitive information; provision with governance. Beneficial cross-effect on O3.

*Case sketch (illustrative).* A field operations unit scored O2 at 54 with good tooling but managers spending hours assembling weekly performance data manually from three systems. Self-serve-reporting variant: a single operational dashboard built around the decisions managers actually made, drawing from the three sources automatically. O2 designed to move ~+7 by the half-yearly, with manual-assembly time as the near-term signal.

## 5.3 O3 — Process and workflow

### Pattern O3-P1 — Targeted bottleneck redesign

**When to use this pattern.** A specific identifiable step creates rework, delay or queue — the surrounding process may be fine. Common validated root causes:
- A reliably-failing team-to-team handoff.
- An approval step at the wrong level (everything escalates).
- A tool-driven artificial constraint.
- A capacity bottleneck on one role family processing a queue.
- A quality bottleneck where rework reliably happens at one step.

**Evidence base.** Theory of Constraints (Goldratt 1984); Lean (Womack & Jones 1996; Liker 2004); business process management (Dumas et al. 2018); process mining (van der Aalst 2016). **Rating: A.**

**Design shape.**
1. Identify the bottleneck with process-mining data, or the friction audit (Tier 3 Module Library) where mining isn't available.
2. Redesign the constraining step specifically — remove, automate, parallelise or re-sequence. Targeted, not wholesale.
3. Adjust the adjacent step — a removed bottleneck often moves to the next-tightest constraint.
4. Measure cycle time/rework/queue before, during and after; iterate to the next constraint if it moves.
5. Name an owner for the process step — without ownership the redesign decays.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Team-to-team handoff | Handoff | Handoff redesign |
| Approvals constrain | Approval-threshold | Threshold change (combine O1-P1) |
| Tool creates the constraint | Tool-constraint | Combine O2-P1 |
| Genuine capacity constraint | Capacity-constraint | Combine O4-P1 |

**Indicative effect.** +6 to +14 on O3.

**Pace of change.** Fast. Among the fastest, most measurable interventions — structural process fixes produce visible cycle-time movement quickly. O3 survey reads half-yearly; cycle-time data is continuous. Good news for client expectations.

**Failure modes.**
- Redesigning the whole process when one step was the problem.
- Moving the bottleneck downstream rather than removing it.
- No process-mining/friction-audit baseline — "bottleneck" becomes opinion.
- Unclear ownership.

**Watch for.** Often interacts with O4 (capacity) and DLP (decision steps). Conditions trip-wire risk if the redesign strips job content without parallel role redesign.

*Case sketch (illustrative).* A loan-processing unit's O3 was 51; Stage 2 found one approval step where every application queued for a single overloaded approver. Approval-threshold variant: routine approvals delegated below the threshold with a sampling-based risk check retained. O3 designed to move ~+10 within a quarter or two, end-to-end cycle time as the lead signal.

## 5.4 O4 — Resource adequacy

### Pattern O4-P1 — Demand management and capacity rebalance

**When to use this pattern.** Sustained capacity stress — overtime, backlog growth, burnout indicators, turnover in constrained roles. Common validated root causes:
- Demand grew faster than capacity without scope reprioritisation.
- Unfiltered demand — the unit accepts work it should decline or route.
- Headcount cut without scope reduction.
- One role family constrained while others have slack.
- No productivity investment to keep pace with demand growth.

**Evidence base.** Job demands–resources (as M1-P1); capacity-planning / workforce-analytics practice; burnout literature (Maslach & Leiter 2008; Bakker et al. 2014). **Rating: B.**

**Design shape.**
1. Run an honest demand-capacity analysis — work asked for vs sustainable capacity; locate the imbalance.
2. Manage demand first — explicit prioritisation, decline-or-defer protocols, routing elsewhere. Many problems resolve without adding capacity.
3. Invest in productivity — tools, process, automation (combine O2-P1/O3-P1).
4. Expand capacity where the gap is structural and durable and other levers are exhausted.
5. Protect sustainable pace through manager/leader practice — the reinforcement that stops the gap reappearing.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Unit accepts work it shouldn't | Demand-filter | Demand discipline |
| Capacity exists, processes inefficient | Productivity-investment | Combine O2/O3 |
| Demand durable, levers exhausted | Capacity-expansion | Headcount |
| One role family constrained, others slack | Internal-rebalance | Reallocation |

**Indicative effect.** +4 to +10 on O4.

**Pace of change.** Mixed. O4 survey is half-yearly; underlying capacity data is monthly. Demand-filter shows fast; capacity-expansion is slow (hiring lead time). Set expectations by variant.

**Failure modes.**
- Capacity expansion into unfiltered demand — same gap, higher cost.
- Demand filtering without leadership cover — overridden within a quarter.
- Productivity investment that doesn't land (new tools that don't displace work).
- Treating burnout as an individual problem when it's a system signal.

**Watch for.** Conditions trip-wire risk where chronic over-demand creates safety/fairness concerns. Beneficial cross-effects on M1, M2 (safety co-erodes with over-demand), retention.

*Case sketch (illustrative).* A support team's O4 was 44 with chronic overtime and rising sick leave. Stage 2 found unfiltered intake — the team said yes to everything. Demand-filter variant: a prioritisation protocol with leadership cover, low-value requests routed elsewhere. O4 designed to move ~+7 by the half-yearly, overtime hours as the lead signal.

### Pattern O4-P2 — Scope and mandate renegotiation

**When to use this pattern.** The capacity gap can't be closed inside the unit — the demand placed on it genuinely exceeds any sustainable capacity, and the fix is to renegotiate the unit's scope or mandate upward/outward, not to rebalance internally. Distinct from O4-P1 (which works inside the unit's own demand and capacity); here the lever sits above the unit, with the sponsor or enterprise. Common validated root causes:
- The unit's mandate has expanded repeatedly without anyone formally resourcing or de-scoping it.
- The unit absorbs work that properly belongs to other functions because no one else will take it.
- Enterprise expectations of the unit are set without reference to its actual capacity.
- The unit is the default catch-all for ambiguous work.

**Evidence base.** Job demands–resources (as M1-P1); role-overload research (Bolino & Turnley 2005, *Journal of Applied Psychology*); organisational boundary and mandate literature. **Rating: B.**

**Design shape.**
1. Quantify the structural over-mandate — what is the unit accountable for, what would sustainable capacity actually support, and what is the gap.
2. Build the evidence pack for the sponsor — the demand-capacity gap expressed in terms the sponsor can act on (service levels at risk, the cost of the status quo in turnover and quality).
3. Design the renegotiation options: formally de-scope (work the unit stops doing, with where it goes); re-mandate (work formally moved to the function it belongs to); or resource (the enterprise funds the gap because the mandate is genuinely required).
4. Sequence the conversation — this is a sponsor/enterprise decision, so the brief equips the sponsor to make the case upward, not the unit to self-resolve.
5. Where renegotiation isn't fully granted, the brief is honest that the residual gap remains and falls back to O4-P1 demand-filtering within the reduced-but-still-excessive mandate.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Mandate crept without resourcing | Re-mandate | Formal scope decision at sponsor level |
| Absorbs others' work | De-scope/transfer | Move work to the right function |
| Genuinely required, under-resourced | Resource-the-mandate | Enterprise funding case |

**Indicative effect.** +5 to +12 on O4 *if the renegotiation succeeds* — but the effect is conditional on a decision outside the unit, which the brief must state plainly.

**Pace of change.** Variable and decision-gated. The renegotiation itself may take a quarter or two of sponsor-level conversation; the O4 effect follows only once the scope decision lands. Set client expectations carefully — this lever depends on an enterprise decision PerformanceVP does not control and the unit cannot force.

**Failure modes.**
- Designing this as a unit-level intervention when it requires an enterprise decision — the unit cannot renegotiate its own mandate.
- A de-scope with no agreed destination — the work boomerangs back.
- Winning resource without managing the demand that caused the overload — the gap reopens.
- Over-claiming the effect when it depends on a decision still pending.

**Watch for.** Conditions trip-wire risk where the structural over-mandate is producing unsafe or unsustainable work conditions — that elevates urgency and may need TW-P3 alongside. Strong cross-effects on M1, M2 and retention once resolved.

*Case sketch (illustrative).* A data team's O4 was 41; Stage 2 found it had become the catch-all for every ad hoc reporting request across three divisions, on top of its core mandate, with no formal resourcing. This was structurally beyond internal rebalancing. Re-mandate variant: an evidence pack quantifying the gap, and a sponsor-level proposal to route routine divisional reporting to a self-serve capability and formally fund the core mandate. O4 designed to move ~+8 *conditional on* the sponsor securing the scope decision — stated as a dependency in the brief.

## 5.5 O5 — Leadership enablement

### Pattern O5-P1 — Targeted manager development

**When to use this pattern.** A specific manager's enabling behaviour drags their team's O5; the unit average may be fine but the affected team's O5 is materially below. Common validated root causes:
- Technically excellent but behaviourally weak at enabling (micromanagement, conflict avoidance, slow decisions).
- Promoted without development.
- Own incentives reward team-blocking behaviour (e.g. tight cost control over enablement).
- Overloaded — span too wide — so enablement is crowded out.

**Evidence base.** Team coaching (Hackman & Wageman 2005); first-line manager research (Gentry 2010); coaching meta-analysis (Theeboom et al. 2014). **Rating: A** for leader effects on team outcomes; **B** for development effectiveness at this outcome.

**Design shape.**
1. Diagnose: OI-5 direct-report perception (Tier 3 Module Library), peer and own-manager feedback, observation where possible.
2. Build a behavioural development plan with specific enabling-behaviour goals (clear direction, removing blockers, coaching, recognising work, fair allocation).
3. Coach using the manager's real decisions and interactions as practice — not abstract courses.
4. Engage the manager's own manager to reinforce and align incentives with enabling behaviour.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Receptive, behaviour changeable | Coaching-led | Individual coaching |
| Overloaded manager | Span-reduction | Coaching + span/role redesign |
| Incentives reward wrong behaviour | Incentive-realignment | Coaching + incentive change above |
| Development not viable | Role-change | Managed role change with dignity |

**Indicative effect.** +5 to +10 on the affected team's O5.

**Pace of change.** Fast. O5 is quarterly cadence — one of the most responsive sub-dimensions. Direct-report pulse can read at 60 days. A relatively quick win where the manager is receptive.

**Failure modes.**
- Generic leadership training instead of targeted behaviour change.
- Avoiding the role-change decision when development clearly fails (>6 months, no movement).
- Coaching a manager whose incentives reward the wrong behaviour.
- Ignoring the team's role in observing/reinforcing the change.

**Watch for.** Beneficial cross-effects on M1, M2, S3 in the affected team. Fairness trip-wire risk where one manager gets development and another with similar shortfalls gets nothing.

*Case sketch (illustrative).* A logistics unit's overall O5 was 64 but one shift manager's team sat at 43 with high turnover. Coaching-led variant: OI-5 diagnosis, real-work coaching on delegation and blocker-removal, the operations director reinforcing. That team's O5 designed to move ~+7 within two quarters.

# Part 6 — Synergy (S) Patterns

S_internal = 0.30(S1) + 0.40(S2) + 0.30(S3), mapped to S ∈ [0.85, 1.15].

## 6.1 S1 — Skill complementarity

### Pattern S1-P1 — Team composition redesign

**When to use this pattern.** The team's skill profile is the wrong shape — duplicated where overlap doesn't help, thin where range is needed. Common validated root causes:
- Hiring reproduced the existing profile without complementarity criteria.
- A reorg merged/split teams without considering skill mix.
- The work evolved but composition didn't adapt.
- Long tenure produced narrow specialisation.

**Evidence base.** Team composition meta-analyses (Stewart 2006; Bell 2007); diversity-performance work (van Knippenberg & Schippers 2007; Joshi & Roh 2009); team design (Hackman 2002). **Rating: B** — effect depends heavily on task interdependence.

**Design shape.**
1. Map the team's actual skill profile against work requirements (use C1 data).
2. Analyse complementarity — where duplicated, where thin, what profile would close the gap.
3. Plan recomposition via hiring, internal mobility, role redefinition or partner access (6–18 months given hiring/transition lead times).
4. Onboard new members with explicit attention to their complementary role; brief the team on the new shape.
5. Review composition against the work annually.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Gap fillable by new hires | Hiring-led | Recruitment |
| Right people exist elsewhere internally | Internal-mobility | Mobility |
| Redefining roles closes the gap | Role-redefinition | Role design |

**Indicative effect.** +4 to +10 on S1.

**Pace of change.** Slow. S1 is annual cadence and composition change is inherently slow. Set client expectations toward a 12-month-plus horizon.

**Failure modes.**
- Hiring more of the same without complementarity criteria.
- Ignoring cohesion impact — recomposition affects the team; design onboarding/norming.
- Composition change without psychological safety — divergent skill is suppressed, not exercised.

**Watch for.** Beneficial cross-effect on C4. Fairness trip-wire risk where recomposition is perceived as targeted exits without due process.

*Case sketch (illustrative).* A data team scored S1 low — five analysts with near-identical SQL skills and nobody who could productionise models. Hiring-led variant: two ML engineers recruited for complementarity, the team rebriefed on the new shape. S1 designed to move ~+7 by the annual refresh.

## 6.2 S2 — Collaboration friction

### Pattern S2-P1 — Ways-of-working redesign

**When to use this pattern.** The calendar is consumed by low-value meetings and coordination cost, leaving insufficient focus time (often >20 meeting-hours/week per IC, fragmented blocks, after-hours patterns). Common validated root causes:
- Meeting practices evolved unconstrained.
- Default norms (60-min, video-on, full attendance) overcommit time.
- Handoffs that should be async became synchronous.
- Specific recurring meetings have outlived their purpose.

**Evidence base.** Collaboration overload (Cross et al. 2016; Perlow et al. 2017); deep-work/interruption cost (Newport 2016; Mark et al. 2008); async-work research (DeRosa & Lepsinger 2010). **Rating: B.**

**Design shape.**
1. Audit meeting load (Workplace Analytics or self-audit); categorise necessary recurring / unnecessary recurring / project-bounded / ad hoc.
2. Reduce — eliminate the unnecessary recurring; cut default durations and attendees; shift status to async.
3. Protect focus time — block-protect half-day blocks 2–3×/week, defended by the manager.
4. Set async-first defaults — decisions go async-first; meetings only where synchronous adds value.
5. Redesign the worst recurring handoff — often the single biggest coordination cost.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Meeting load is the primary cost | Meeting-reduction | Reduction |
| Time fragmented, meetings not the only cause | Focus-protection | Focus-block protection |
| Async-capable in tooling, not in practice | Async-shift | Norm change |
| Cost concentrated in specific handoffs | Handoff | Redesign worst handoffs |

**Indicative effect.** +6 to +14 on S2.

**Pace of change.** Fast. S2 is quarterly cadence and meeting load can change in a fortnight — among the fastest, most visible interventions. The classic quick win.

**Failure modes.**
- Cutting meetings without redesigning the coordination they did — work falls through gaps.
- Reverting within two quarters without sustained norms.
- Cutting unit meetings while senior leaders keep calling default-everyone meetings.
- Treating focus time as optional — sacrificed at the first scheduling conflict.

**Watch for.** Strong beneficial cross-effect on M1 (meeting load is a top engagement detractor). Conditions/fairness interaction in reverse if meeting reduction is seen as exclusion from decisions — set attendance criteria.

*Case sketch (illustrative).* An engineering team scored S2 at 47; Workplace Analytics showed 24 meeting-hours/week per IC and almost no unbroken focus time. Meeting-reduction variant: recurring meetings halved, defaults cut to 30 minutes and optional attendance, two protected focus afternoons a week. S2 designed to move ~+10 within one quarter.

## 6.3 S3 — Conflict health

### Pattern S3-P1 — Conflict-health practices

**When to use this pattern.** The team has too little task conflict (false consensus, suppressed disagreement) or too much relationship conflict (interpersonal friction). TSI-3 distinguishes them; the intervention differs. Common validated root causes:
- *Low task conflict:* low safety, surface agreement, disagreement re-emerging as passive resistance.
- *High relationship conflict:* interpersonal patterns consuming team energy.
- Both coexisting — relationship friction substituting for the task disagreement the team can't have safely.
- A specific dyad/trio accounting for most relationship conflict.

**Evidence base.** Task vs relationship conflict meta-analyses (De Dreu & Weingart 2003; de Wit et al. 2012); safety-conflict link (Edmondson); conflict-management frameworks (Behfar et al. 2008). **Rating: A** for the distinction and effects; **B** for intervention effectiveness.

**Design shape.**

*Low task conflict:*
1. Establish norms that invite dissent — assigned-skeptic roles, pre-mortems, structured devil's advocacy.
2. Address the underlying safety condition (usually combine M2-P1/M2-P2 — low task conflict is often a downstream M2 signal).
3. Recognise and reward disagreement when it surfaces — leader behaviour rewards the dissenter.

*High relationship conflict:*
1. Locate it — diffuse team-wide pattern, or concentrated dyad?
2. Dyadic → structured mediation/facilitated conversation with explicit norms; role separation if reconciliation isn't feasible.
3. Team-wide → norm reset (sometimes external facilitation) with explicit conflict-handling norms.
4. Fix the structural source if present — relationship conflict is sometimes downstream of unfair workload, recognition or decision rights.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Suppressed disagreement | Low-task-conflict | Norm change + M2 work + dissent recognition |
| Specific dyad conflict | Dyadic-conflict | Mediation + role separation if needed |
| Team-wide friction | Team-wide-pattern | Facilitated reset + norms + structural fix |

**Indicative effect.** +4 to +9 on S3.

**Pace of change.** Moderate. S3 is half-yearly cadence; behavioural change with team reinforcement. Dyadic resolution can be faster (a quarter) if the dyad is resolvable. Set the real read at the half-yearly.

**Failure modes.**
- Dissent-welcoming without behaviour change — subtle punishment continues, erodes M2 further.
- Mediation without authority to enforce outcomes.
- Treating structural relationship conflict as a personality problem.
- Ignoring a high-relationship/low-task signal — suppressed substance venting on people; address M2 alongside.

**Watch for.** Strong M2 link (often joint intervention). Fairness trip-wire risk where conflict has structural unfairness as cause.

*Case sketch (illustrative).* A leadership team scored S3 low with TSI-3 showing near-zero task conflict and elevated relationship friction — they avoided real disagreement and it leaked into personal tension. Low-task-conflict variant (with M2-P1): pre-mortems and an assigned-skeptic norm installed, the underlying safety issue addressed, the chair rewarding surfaced dissent. S3 designed to move ~+6 by the half-yearly.

# Part 7 — Decision Latency Protocol (DLP) Patterns

The DLP sits across O1, O3 and O5; patterns are organised by decision class because the levers differ.

## 7.1 DLP-P1 — Operational decision latency reduction

**When to use this pattern.** The DLP sample shows operational-class latency above the archetype norm; cost shows in slow customer response, delivery delay, and frustration that lowers M3. Common validated root causes:
- Approval layers too deep; first-line decisions escalate.
- Delegation thresholds too conservative (often a legacy of an earlier risk event).
- The latency is information-gathering, not authorisation.
- A specific manager bottlenecks through hoarding or slow response.

**Evidence base.** Decision-rights literature (Brickley et al. 2009); RAPID practice (Bain); time-based competition (Stalk 1988). **Rating: B.**

**Design shape.**
1. Diagnose from the DLP sample which operational decisions are slow and where latency accumulates.
2. Simplify decision rights — raise thresholds, delegate downward, remove redundant approval steps.
3. Where latency is information-gathering, reduce information-acquisition cost (combine O2-P1) rather than changing rights.
4. Address a bottleneck manager via O5-P1 if that's the cause.
5. Redesign residual risk management where thresholds were set conservatively post-incident — what now catches genuinely high-risk decisions?

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Approval thresholds block | Threshold-raise | Structural threshold change |
| Latency is information-gathering | Information-access | Combine O2-P1 |
| Bottleneck manager | Bottleneck-manager | Combine O5-P1 |

**Indicative effect.** DLS operational-class +8 to +18; flows through to O1 and often M3.

**Pace of change.** Fast. DLP operational class is quarterly. A structural threshold change shows quickly. A quick win where authorisation (not information) is the block.

**Failure modes.**
- Delegating authority without the capability/information to use it well.
- Raising thresholds without managing the risk that justified them.
- Stopping at the threshold change without the cultural "this decision is yours" reinforcement.

**Watch for.** Beneficial cross-effects on O1, M3, M1. Conditions trip-wire risk if delegation pushes safety-critical decisions to under-qualified roles.

*Case sketch (illustrative).* A field-service unit's operational DLS was poor — routine part-replacement approvals took days, escalating to a regional manager. Threshold-raise variant: approval delegated to the technician below a dollar threshold with monthly sampling retained. Operational DLS designed to move ~+12 within a quarter, with O1 and M3 benefit following.

## 7.2 DLP-P2 — Tactical and strategic decision latency reduction

**When to use this pattern.** Tactical (cross-functional, multi-stakeholder) or strategic (board/exec) decisions take too long; cost is opportunity loss and eroded confidence in the organisation's ability to decide. Common validated root causes:
- Governance forums with unclear authority; decisions re-debated across forums.
- Unbounded consultation; consensus sought where authority should resolve.
- Poor decision packaging — decision-makers can't tell what's being asked.
- The decision body meets too infrequently for the decision pace.

**Evidence base.** Governance design (Tricker 2019; Wageman et al. 2008); fast strategic decision-making (Eisenhardt 1989; Eisenhardt & Bourgeois 1988). **Rating: B.**

**Design shape.**
1. Inventory decisions against governance bodies; find overlap/contradiction.
2. Redesign forums — clear authority, clear scope, frequency matched to decision pace.
3. Install decision-packaging discipline — standard format: what's asked, options, recommendation, risk.
4. Set consultation boundaries — distinguish "consult" from "co-decide."
5. Track decisions with rationale; check the log to avoid re-debating.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Governance overlap/contradiction | Forum-redesign | Forum authority + scope |
| Forums can't decide on fuzzy asks | Decision-packaging | Packaging discipline |
| Consensus sought beyond need | Consultation-discipline | Consult vs co-decide |

**Indicative effect.** DLS tactical +6 to +14; strategic +5 to +12.

**Pace of change.** Moderate-slow. Tactical DLS is half-yearly, strategic annual. Slower than operational by the nature of the decision classes.

**Failure modes.**
- Governance redesign without authority enforcement.
- A decision-packaging template that fills with the same fuzziness.
- Over-tight governance that suppresses dissent (speed at the cost of quality).

**Watch for.** Beneficial cross-effects on O1 (cascade), M4 (purpose — strategic intent reaches the work), engagement.

*Case sketch (illustrative).* An exec team's tactical DLS was poor — cross-functional investment decisions bounced between three committees. Forum-redesign variant: clear decision authority assigned per decision type, a standard decision-paper format, a decision log. Tactical DLS designed to move ~+9 by the half-yearly.

## 7.3 DLP-P3 — Information-latency reduction

**When to use this pattern.** The DLP sample shows the wait is in *getting the information to decide*, not in authorisation — the decision-maker has the authority but can't act because the data, analysis or input arrives too slowly. Distinct from DLP-P1 (which fixes authority); here the rights are fine and the bottleneck is information flow. Common validated root causes:
- The data needed to decide is scattered, manual to assemble, or owned by someone slow to provide it.
- Decisions wait on analysis that has no service standard or owner.
- Required input from another team or function has no agreed turnaround.
- Decision-makers lack a standing information view and re-request the same data each time.

**Evidence base.** Information-processing view of organisations (Galbraith 1974, *Interfaces*); decision-support and management-information research; the time-based competition literature (Stalk 1988). **Rating: B.**

**Design shape.**
1. From the DLP sample, isolate the decisions where latency accumulates *before* the decision point — in information-gathering, not authorisation.
2. Identify the specific information bottleneck — which data, which analysis, which input, owned by whom.
3. Fix the information flow: a standing decision-information view (dashboard/report) for recurring decisions; a service standard and owner for the analysis; an agreed turnaround for cross-team input.
4. Where the root cause is tooling or data access, combine with O2-P2 (information access) — the information-latency fix and the access fix are often the same work.
5. Confirm against the next several real decisions that the information now arrives ahead of the decision point.

**Variants — pick by root cause.**

| Validated root cause | Variant | Dominant lever |
|---|---|---|
| Recurring decision, data re-assembled each time | Standing-view | Decision dashboard/report |
| Analysis has no owner or standard | Analysis-SLA | Service standard + owner |
| Cross-team input is slow | Input-turnaround | Agreed turnaround + escalation |

**Indicative effect.** DLS improvement +6 to +14 on the affected class; flows through to O1 and O3.

**Pace of change.** Fast where the fix is a standing view or an agreed turnaround (operational class, quarterly); moderate where it requires data-access or tooling work (combine O2-P2). A relatively quick win where the information bottleneck is well-defined.

**Failure modes.**
- Building a standing view nobody maintains — it goes stale and decisions revert to ad hoc data pulls.
- Setting an input turnaround without an escalation path when it's missed.
- Confusing information latency with authority latency — fixing rights when the real wait was data (and vice versa); Stage 2 must distinguish these.

**Watch for.** Beneficial cross-effects on O3 (process) and O1. Strong overlap with O2-P2 — often the same design. No direct trip-wire risk.

*Case sketch (illustrative).* A pricing team's operational DLS was poor, but the managers clearly had authority — the wait was a three-day turnaround on the margin analysis each pricing decision needed, owned by an overloaded analyst with no standard. Standing-view variant: a self-serve margin dashboard built for the recurring decision types, with the analyst's manual work reserved for non-standard cases. Operational DLS designed to move ~+10 within a quarter.

# Part 8 — Trip-wire Remediation Patterns

Trip-wires (pay equity, fairness, basic conditions) are critical-finding overlays, not weighted contributors to M. Three constraints apply to all three patterns:

- **Legal exposure.** Trip-wire issues are often legally sensitive. PerformanceVP designs the *organisational* remediation; the client engages legal counsel for legal advice (Intervention Design Handbook Part 7.6). The brief directs the client to counsel explicitly.
- **Structural fix, not just survey movement.** The deeper success criterion is the structural fix (completed audit, fairness process, conditions remediation), not just the trip-wire item recovering.
- **Cross-cutting lift.** Trip-wire remediation often lifts M1, M2, S3 and engagement broadly — capture this, but the primary criterion is the trip-wire.

## 8.1 TW-P1 — Pay equity remediation

**When to use this pattern.** Pay-equity trip-wire fired (<60). Common validated root causes: compensation drift (new hires above incumbents); inconsistent band administration; demographic gaps unexplained by role/performance/tenure; opaque pay communication driving perception ahead of reality.

**Evidence base.** Pay-equity literature (Blau & Kahn 2017); procedural justice (Greenberg 1990). **Rating: A** construct; **B** remediation effectiveness.

**Design shape.**
1. Pay-equity audit *with legal counsel* — identify gaps unexplained by role/performance/tenure.
2. Remediate unexplained gaps (often a multi-year plan to avoid budget shock).
3. Change the process — calibrate pay decisions; transparent bands and adjustment criteria; ongoing equity monitoring.
4. Communicate how pay is set, even where individual pay isn't disclosed.

**Indicative effect.** Trip-wire recovery above threshold; gap reduction; perceptual lift on related items.

**Pace of change.** Slow. Genuine remediation (especially staged correction) runs 6–24 months; perception can move faster once visible and trusted.

**Failure modes.** Partial remediation perceived as cosmetic (backlash risk). Audit without follow-through.

**Watch for.** Strong beneficial effects on M1, M2, engagement when visible and trusted.

*Case sketch (illustrative).* A unit fired the pay-equity trip-wire at 51; an audit (with counsel) found new hires materially above tenured staff in the same band. A staged correction over 18 months plus transparent band communication was designed; the trip-wire designed to recover above 60 as correction landed.

## 8.2 TW-P2 — Fairness remediation

**When to use this pattern.** Fairness trip-wire fired (<60). Common validated root causes: specific manager/team patterns of unfair treatment; process-fairness gaps in PM, opportunity allocation or recognition; cultural patterns disadvantaging certain groups in informal allocation.

**Evidence base.** Organisational justice meta-analyses (Colquitt et al. 2001; Cohen-Charash & Spector 2001). **Rating: A** construct; **B** remediation effectiveness.

**Design shape.**
1. Fairness investigation (with legal counsel, often HR-led) — identify the specific patterns.
2. Structural fix — process redesign for unfair processes; manager intervention where a manager is the cause.
3. Formalise allocation criteria where informal allocation produces unfair outcomes.
4. Communicate the issue, the response, and the ongoing accountability mechanism.

**Indicative effect.** Fairness recovery; lift in M2 and M1.

**Pace of change.** Moderate. Structural fixes 3–12 months; perception follows visible action.

**Failure modes.** Remediation perceived as targeting groups can fire fairness from another direction. Investigation without structural change.

**Watch for.** Cross-effects with M1, M2, S3.

*Case sketch (illustrative).* A fairness trip-wire at 49 traced to opaque, manager-discretion promotion decisions perceived as favouritism. Formalised promotion criteria with a calibration step were designed, plus transparent communication; the trip-wire designed to recover, M2 lifting alongside.

## 8.3 TW-P3 — Basic conditions remediation

**When to use this pattern.** Conditions trip-wire fired (<60). Common validated root causes: inadequate physical workspace (safety, ergonomics, capacity); chronically deficient tools/equipment; unsustainable work-time conditions; unaddressed safety (WHS) issues.

**Evidence base.** Job demands–resources; safety-climate meta-analysis (Christian et al. 2009); ergonomics/workplace-design literature. **Rating: A** construct; **B** intervention effectiveness.

**Design shape.**
1. Conditions audit — what specifically is sub-standard (workspace, tools, time, safety)?
2. Remediate per category with the specific structural fix.
3. Install ongoing monitoring — conditions audits cycled; WHS process reviewed.

**Indicative effect.** Conditions recovery; WHS incident-rate reduction; downstream M1 and retention lift.

**Pace of change.** Variable — process changes fast; workspace redesign slow (3–24 months by scope).

**Failure modes.** Remediating the symptom (e.g. equipment) while ignoring the work-time condition that also fired the trip-wire.

**Watch for.** Cross-effects on M1, M2, O4 (where time is the condition).

*Case sketch (illustrative).* A warehouse unit's conditions trip-wire fired at 46 over equipment reliability and shift design. A combined remediation — equipment refresh plus a shift-pattern redesign with WHS review — was designed; the trip-wire designed to recover, with incident rate as the structural confirmation.

# Part 9 — Maintenance and Evolution

## 9.1 How patterns are added and refined

A living document. Patterns enter via three routes:
1. **Engagement experience** — where an engagement designs an uncatalogued pattern, the analyst documents it at closure (Intervention Design Handbook Part 9.4) for the next refresh.
2. **Research updates** — significant new evidence refreshes the affected entry.
3. **Expected-vs-actual data** — as Tracking subscriptions show whether interventions moved their targets, indicative ranges tighten, evidence ratings re-evaluate, failure modes refine.

## 9.2 Refresh cadence and propagation

Annual refresh with the document set, plus material out-of-cycle refreshes where warranted. When the Library refreshes, check consistency with: Intervention Design Handbook Part 7 (summary pointer), Diagnostic Delivery Handbook Part 8.5 (seed-list pointer), the Project Knowledge briefing, and the Document Map.

## 9.3 Pattern naming

Patterns are referenced by name (`[sub-dimension]-P[number]`) in the Diagnostic Workbook and Intervention Design Workbook, so a refresh propagates automatically into the next engagement's workbooks. Names are stable across refreshes even when content evolves.

Honest about what this version still doesn't carry, pending engagement data:
1. **Empirically-calibrated movement ranges** — current ranges are evidence-informed estimates; real expected-vs-actual data replaces them.
2. **Implementation-quality dependency, quantified** — currently the qualitative assumption in Part 1.4.
3. **Real anonymised case studies** — the current sketches are illustrative composites; real engagement cases supplement them.
4. **Industry-archetype variants** — deeper per-archetype design guidance once PerformanceVP has industry-spread experience (light industry notes currently sit in pattern *Watch for* lines).
5. **Additional patterns** where live engagements surface intervention shapes not yet catalogued.
